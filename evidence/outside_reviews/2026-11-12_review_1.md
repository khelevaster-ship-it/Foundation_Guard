---

I treated the document as the review prompt and the attached ZIP as the kit under review. I ran the code directly, created scratch Git repositories, and tried attacks rather than relying only on the documentation.

1. Verdict
I would not yet trust FoundationGuard to guard a project unattended overnight as a security boundary, but I would trust it as a fairly serious mistake-prevention layer with an important caveat: its strongest claims are not all true. I found two concrete claim-breaking weaknesses in C4 and C10, plus several limitations that are explicitly admitted by the kit and therefore should not be counted as new findings. The architecture is substantially stronger than a typical AI-written guard, but I would not release it beyond beta until the two concrete issues are fixed and the full 219-rule proof run is independently reproduced.

The most important finding: C4
This is the one I would fix first.

The kit's logic is essentially:

"If this is a new test and the change only adds a test, let it through."

That is a reasonable optimization until the new test itself changes shared state.

For example, my scratch Python project had:

import shared

def test_new():
    shared.config["value"] = 1
    assert shared.config["value"] == 1

The guard allowed the new test with no owner prompt.

The same conceptual attack worked in C++:

IMPLEMENT_SIMPLE_AUTOMATION_TEST(FNew, "Game.New", ...)
bool FNew::RunTest(const FString& P)
{
    Shared = 0;
    TestTrue(...);
    return true;
}

and GDScript:

func test_new():
    GlobalState.items.clear()
    assert GlobalState.items.size() >= 0
The important point isn't that those exact examples are malicious. It's that a new test can deliberately alter the environment in which later tests execute while still looking like "only adding a test."

That directly contradicts C4's wording.

3. Ways around the guard I found
A. C1 — dynamic Python construction
Known limitation, not a new finding:

python -c "import os; os.system('g'+'it push --force origin main')"

The guard allows it.

Likewise:

python -c "import subprocess; subprocess.run(['g'+'it','push','--force','origin','main'])"

The reason is visible in fg/guard.py:221-232: it looks for literal strings containing git and literal argument-list strings.

This is exactly the kind of bypass covered by the kit's own statement that it is not a sandbox.

B. C3 — dynamic guard-file path
Also within the admitted text-analysis limitation:

python -c "open(chr(102)+chr(103)+'/guard.py','w').write('x')"

The guard did not ask.

Again, this is serious in an absolute security sense, but I would not call it a new defect against the stated design. The documentation already says a determined program can bypass text inspection.

C. C4 — new-test shared-state mutation
This one is a new finding, because the kit explicitly claims the new-test exemption handles this category.

Python:

shared.config["value"] = 1

C++:

Shared = 0;

GDScript:

GlobalState.items.clear()
All were accepted in newly added test files.

4. False alarms
There are legitimate reasons I would expect an owner to occasionally get annoyed:

git checkout -- file is treated as destructive even if the owner knows the file is disposable.
git reset --hard is blocked even when the working tree is already clean.
Deleting or force-renaming branches is blocked.
Changes to committed tests require an owner interaction even when the change is a legitimate test refactor.
Changes to the kit's own records/settings require an owner interaction.
Some shell commands that merely mention a guarded filename in a writing context can produce an ask because the parser cannot prove whether the name is data or a destination.
The asset ledger can require paperwork for assets that are legitimately generated or internally produced unless the project records that explicitly.
The deterministic-math rules can potentially object to perfectly legitimate uses of random/time/math APIs when those uses aren't part of simulation determinism.
I don't consider these fatal. In fact, the design choice to err toward asking rather than silently permitting is generally appropriate for the target user.

The danger is making the owner see enough harmless prompts that they eventually disable the kit.

5. Answers to the owner's questions
1. Overnight
With gather_asks enabled, the kit does a good job of separating ordinary test additions from changes that must wait for the owner.

The worst thing a helper can do within the text-inspection model is alter a newly added test so that it changes shared state, or otherwise exploit something the weakening detector doesn't understand. My C4 examples demonstrate that this is possible.

Could it reach GitHub? Yes, in principle, if the helper constructs a bypass dynamically, because the kit is not a sandbox. The exact example I tested was dynamically constructing git push --force. That limitation is already explicitly documented.

The important distinction is:

The overnight design is reasonably safe against a normal cooperative helper making ordinary shell calls. It is not a security boundary against an arbitrary program controlled by the helper.

2. Honest but stubborn helper
The easiest realistic route isn't an exotic exploit.

It is:

"I'll put the operation into a script and run the script."

The kit explicitly admits that script contents aren't read.

That is exactly the kind of thing an otherwise honest helper might do if it encounters a block: create fix.py, cleanup.sh, or another helper script and invoke it.

The kit's documentation is honest about this. The problem is therefore not that FoundationGuard secretly fails; it is that the user needs to understand that "blocked command" doesn't mean "blocked action."

3. Weakened tests
This is where my strongest result is.

Python: a new test can mutate imported shared state through an operation the detector doesn't classify as a shared-state modification.

shared.config["value"] = 1

C++: a new test can modify a shared bare variable:

Shared = 0;

GDScript: a new test can mutate shared state through a method call:

GlobalState.items.clear()
The current detector is substantially better than a simple regex—especially for C++ declarations and Python global-state mechanisms—but it is still a syntactic heuristic.

This is exactly the place where I would change the policy rather than endlessly adding regexes.

4. Three APPROVED rows
I could not honestly claim to have independently broken three arbitrary rows out of all 219 in this run.

I did independently exercise the break-to-prove machinery and successfully reproduced:

F001 — PROVEN
F100 — PROVEN
F219 — PROVEN in an earlier direct run
The complete --all run exceeded my execution window. That means C6 remains unverified by this review, not that it failed.

The architecture of prove.py is sensible: it runs the normal check, applies the recorded break, requires the check to fail, and reverses the patch afterward (fg/prove.py:26-45). But that is exactly the sort of system where I would want an independent full run before accepting the 219 claim.

5. False alarms
The biggest risk is not one spectacular false alarm.

It's prompt fatigue.

If an owner repeatedly gets asked about:

legitimate test refactors,
harmless file moves,
generated assets,
normal cleanup,
benign math,
routine dependency changes,
they may eventually approve everything or disable the kit.

The current "plain words" work is therefore important. The catch log and explicit distinction between FoundationGuard's prompt and the AI tool's own prompt are particularly useful.

6. Plain words
The documentation is unusually candid for an AI-produced safety tool.

The strongest sentence is effectively:

This is a guard against mistakes, not a sandbox.

That is exactly the warning a non-programmer needs.

The potentially misleading part is stronger claims such as "covers pushes hidden inside Python" or "every other copy" when the implementation actually means every case the text analysis can recognize and every copy whose remote identity matches its comparison method.

I would tighten those claims rather than hide the limitations.

7. Release
Before outside users install it, I would require:

Must change

Fix C4's new-test/shared-state hole.
Fix the asset-format coverage problem.
Fix or qualify C9's "every copy" claim.
Get an independent complete 219/219 proof run from a fresh checkout.
Have at least one non-Claude reviewer attack the kit from scratch.

Fail-closed behavior.
The tested-commit mechanism.
The separate pre-push hook.
The owner-approval model.
Gathered asks.
The catch log.
Break-to-prove as a stale-check detector, provided it isn't described as complete coverage.
The beta/AI-made disclosure.
Bottom line
The interesting thing about this review is that I didn't find a collapse of the architecture. I found something more useful: the architecture works, but two claims are presently stronger than the implementation warrants.

The C4 issue is the one I'd treat as a release blocker. The C10 issue is comparatively straightforward. C9 needs either a small robustness fix or narrower wording.

And the most important independent observation is that the kit's own stated limitation really is real: I was able to construct dangerous operations dynamically and get them past the textual guard. That doesn't make FoundationGuard fraudulent—the documentation explicitly says this can happen—but it means I would keep its positioning firmly at "AI-agent safety/guardrail layer" rather than "security system."

A very useful next step would be a second adversarial pass focused specifically on C4, because that is the finding most likely to expose additional classes of "new test" side effects beyond the three I already reproduced.
