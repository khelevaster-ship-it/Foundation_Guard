## The review

I would not trust FoundationGuard to watch a project while its owner sleeps. In Claude Code, a helper can turn the guard off, forge the "this commit passed" note, or check out a branch it created a minute earlier, and the check that is supposed to put that back either does not run or treats it as allowed. I pushed the resulting untested commit to a remote. The older word-by-word blocks mostly hold, and the pre-push hook still stops a bad push when it is actually the hook Git runs, but that is not enough for a night alone.
Check after every step (C11) and git settings (C12)
C11 does not hold. Three different steps leave a guard-file change in place with no yes:
A script sets "parts": {"guard": "off"} during the step. steps.after then returns without comparing anything, because the guard is already off (fg/steps.py line 568). No "PUT BACK", no catch-log line. The same script's hooksPath = /dev/null stays too.
A script waits until after that check, then writes .foundationguard/passed_commit. The next step's start takes it as the owner's edit (fg/steps.py lines 335–362). The guard is still on. A later git push from another script matches that note and the remote updates.
A script builds a commit with plumbing (working tree untouched), points a new branch at it, and the next step is git checkout of that branch. The guard allows the checkout. The check keeps the files because the branch tip already existed when the step began (fg/steps.py lines 423–440).
C12 holds only for the keys in RISKY. core.hooksPath, aliases, credential.helper, include.path, core.sshCommand, filter.*, protocol.*.allow, and sequence.editor were put back. Programs Git actually runs that are not in that tuple stay, and two of them ran.

The questions
Overnight. With gather_asks on, the worst case is not a weakened test (that correctly waits for a yes). It is finding 1 or 2. By morning a feature branch on the remote can hold untested work, a test that was loosened, and a project whose guard is off, with no "PUT BACK" line. I saw that push succeed against a local bare remote. It would reach GitHub on any branch that does not have branch protection. A protected branch that requires a check can still reject it. That is the lock the kit already points at, and a night of Claude Code does not replace it.
Make it stick. Yes. Smallest, one step: write tools/off.py that sets parts.guard and parts.push to off in foundationguard.json, then run python tools/off.py as the helper's command. The guard allows it (it does not read the script). The after-step check prints nothing. The file stays off. Then git push of a new commit. To keep the guard looking on, use finding 2 instead: after a bad commit, tools/later.py sleeps 2 seconds and writes that commit's id into .foundationguard/passed_commit; the next git status keeps it; tools/ship.py runs git push.
Honest but stubborn. The after-step message tells the helper to use Edit or Write, which asks, or to stop. A helper that only wants the task to finish, and has just been told its edit was reverted, will often "fix the tool" by turning it off. The easiest stumble is finding 1: a few lines of Python, an ordinary command, no box. The message never appears, so nothing pushes it back toward asking. With gather_asks on, the honest path for tests is fine; the stumble is touching foundationguard.json or the hook when a push is refused.
Weakened tests. Python, new file, called only adds, and the step kept it: g = __import__("game"); g.compute = lambda: 5 inside test_0, with assert g.compute() == 5. Later tests in the same run see the replaced function. C++ tests/FooTest.cpp: GetSettings().Seed = 1; and Settings->Set(1); are only adds; Shared = 0; and #define EXPECT_EQ(a, b) (void)0 are caught. GDScript: should_skip_script that returns true, and var g = GlobalState; g.items.clear(), are only adds. The first three of those are the open gaps from review 4 (findings 9 and 10); they still work.
Checks that don't bite. F241's test puts back a sed and a reversed-path writer. It does not notice finding 1: the same promise ("however it was written") fails when the write turns the guard off. F247's test checks out a branch made before any helper step. It does not notice finding 3, a branch the helper created on the previous step. F254's test puts back hooksPath and an alias. It does not notice difftool.*.cmd or core.alternateRefsCommand, which stay and which I ran. I did not run prove.py --all; those three tests would still pass, because they never try these breaks.
False alarms. Finding 6 is the one that would make me turn it off: my own save, reverted, because a helper had started a background command. Next is a night without gather_asks, where every script or sed touch of an existing test is reverted and the helper is told not to try again. The "doesn't look weaker" box on a loosened test is how an owner says yes to the wrong thing (finding 4).
Plain words. The README says force pushes are stopped "in every spelling", that a guard file changed without a yes is "put back at once, however it was written", and that the yes script "however the command is written, opens your box." None of those three is true (findings 1 and 7, and the hidden spellings above). The catch log line "taken as the owner's own change" is the dangerous one: it is what a delayed helper write is called. The README also says 252 approved rows; APPROVED.md has 257. The guide's limit that "a guard file a script changes is still put back" is false for a script that turns the guard off.
Release. Do not hand this to anyone else until findings 1–4 are fixed and the missed Git program settings (finding 5) are put back. Say in the first screen, not only in the limits, that GitHub branch protection on every branch that matters is required, and that this kit will not save an unattended night by itself. Fine as they are: the named blocks for F229–F235, the fast-forward hook when the hook is still installed, free addition of real new tests, gathered asks for ordinary test edits, and failing closed when the guard crashes. The beta label and "no human has reviewed this" are honest and should stay.
