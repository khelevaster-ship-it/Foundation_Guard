Verdict
I would not trust FoundationGuard to fully guard a project while its owner sleeps. The design is careful, fail-closed on crashes, and the majority of its own tests + prove suite pass, but the command guard is purely textual and several realistic ways of building a blocked command at runtime (shell variables, command substitution, nested exec inside python -c) are currently allowed through. That breaks the central "lost work is blocked even when hidden" claim. GitHub branch protection with required checks is still the only real lock; everything on the machine is friction plus an alarm.

False alarms
Any direct git push (when push_only_via_wrapper is on) – intentional, but an owner who is used to pushing from the IDE will hit it constantly.
Edits or shell writes that touch anything under the configured guard_paths / kit files / APPROVED.md – again intentional, but noisy if the owner is iterating on tests or the kit itself.
Ordinary git reset --soft, git clean -n, git push --dry-run are correctly allowed; the kit is not overly aggressive on the dry-run / soft variants.
Answers to the owner's questions
Overnight (gather_asks on)
Worst realistic case without the owner noticing: a helper builds a force-push or history rewrite via the dynamic constructions above and runs it; or it writes a script that later does the same with --no-verify. With gather_asks the upload itself is still held until the owner says yes, so nothing reaches GitHub unless the helper also finds a way around the pre-push hook (script + --no-verify, or a direct GitHub API call with a token). The records of "what passed" are ordinary files, so a determined helper can also rewrite them.
Honest but stubborn helper
The easiest stumble-upon bypass is exactly the ones listed above: put the dangerous command in a variable or $(...) and eval/run it, or write a one-line Python/bash script and execute the script. The kit never reads the contents of .py/.sh files that are later run.
Weakened tests that look like "only adds"
Python: a new test file that does import target_module; target_module.SOME_GLOBAL = ... or monkey-patches a fixture used by other tests.
C++ / Unreal: a new TEST(...) or automation test that constructs a UObject / mutates a GetMutableDefault<>() or a static that other tests rely on.
GDScript: a new test that changes an autoload singleton or a scene that is shared.
The kit's "only adds tests" heuristic is purely textual and does not execute or deeply analyse side-effects.
Checks that don't bite
I did not have time to systematically break three arbitrary APPROVED.md rows beyond the C1 cases already shown. The prove suite exists precisely to catch the "broken on purpose" case; the risk is always the other ways of breaking the feature that the planted break does not exercise (already listed as a known limit).
False alarms that would make an owner turn the kit off
Being forced to use the kit's push wrapper for every upload.
Any edit that touches a test file after it has been committed (even a comment or a small refactor).
The first time a helper tries a force-push or reset --hard and gets a hard block.
Ordinary non-guard edits and pure "add new tests" are free, which is good.
Plain words
The README and the permission-box texts are mostly clear for a non-coder. The main risk is that "the kit asked" versus "the AI tool asked" can still feel the same, and the dynamic-command gaps are invisible to someone who cannot read the command that was blocked (or not blocked).
Release readiness
Before outsiders use it:
Close the dynamic-construction holes in C1 (and the corresponding C7 paths).
Make the "records are just files" and "script files are never read" limits even more prominent.
Add a short "what a non-coder must still do on GitHub" checklist that is impossible to miss.
Everything else (prove suite, fail-closed, gather_asks, multi-copy coverage, the 219 rules) is already in a usable beta state for a careful owner who keeps branch protection on.
What I could not fully check
Full end-to-end install into a fresh Unreal/Godot/web project and overnight gather_asks simulation (would need a real AI-tool session).
Exhaustive break of every one of the 219 APPROVED rows (the prove suite does the planted breaks; I did not invent new breaks for each).
Real Copilot / Codex / Cursor sessions (only the documented adapter input shapes were exercised by the kit's own tests).
Whether the same dynamic constructions also defeat guard_touch for every write primitive once a full foundationguard.json with populated guard_paths is present (very likely, given how check_line works).
The kit is a serious, thoughtfully engineered piece of work for something written entirely by Claude models. Closing the dynamic-command gaps would make the "while the owner sleeps" claim far more credible.
