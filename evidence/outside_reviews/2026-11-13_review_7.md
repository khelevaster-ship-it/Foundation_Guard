## The review

Here are all four. "TESTED" means I ran it in a scratch project. "READ" means I only read the code or docs. The kit's own 275 tests all passed here (Linux, 3½ minutes).
1. Setup: does it protect what you think it does?
The biggest finding: after the kit's own setup, your tests are not guard files at all. (TESTED)
I ran fg/setup.py --solo on a small project, the way AGENT_SETUP.md says. The foundationguard.json it wrote has no guard_paths, the setting that lists the test folders to guard. Neither setup nor AGENT_SETUP.md ever tells the helper to add one.
Next I changed a test from == 5 to >= 0 with the Edit tool, and then with sed. Neither asked. Nothing was put back, and the gate passed.
Every earlier review, and the kit's own tests, added "guard_paths": ["tests/**"] by hand. That's why nobody saw this.
What still protects you: the upload stops if the test behind an approved row changes (READ, in fg/cards.py), and the nightly re-break would catch a check that stopped biting. Tests you never approved have no protection at all.
Fix: setup should write guard_paths from the test folders it finds. It should also include the test runner's own settings files at the project's top level (conftest.py, pytest.ini, pyproject.toml, .gutconfig.json and the like), since they change what every test does. After that, it should print the list in plain words so you can check it.
--solo turns off "no pushes straight to main". (TESTED) The settings file it wrote says "protected_branches": []. The README lists that block under "What it stops" and doesn't mention the exception. Either --solo should keep main protected, or the README and setup should say plainly that it doesn't.
2. False alarms
These are in rough order of how likely they are to make you turn the kit off.
New since review 6: your own edits to the kit's switches are put back. (READ, fg/between.py) If you edit foundationguard.json or .claude/settings.json yourself between steps, the kit puts it back unless the remote branch already has that exact file. You might add a setting in Notepad, or change your AI tool's environment or hooks. The kit only keeps changes to permission rules. The message tells you to ask a helper to make the change, which feels backwards when it's your own file. Add a plain way for you to accept your own change, such as the existing steps.py --accept behind the kit's box, and name it in the message.
git stash of a guard file is put back, and the stash pop afterwards fails. This is a stated limit, but helpers reach for stash out of habit and get confused by the failure.
A pull that can't reach the remote is put back. If the internet drops overnight, a helper can get stuck in a loop.
git checkout -- file is blocked even on an unchanged file. This was kept on purpose and is documented. It's a small but frequent annoyance.
git remote set-url and gh auth setup-git are put back when a helper runs them. That's fine, but the helper is told "Don't try another way round" and then stops. With you asleep, that means a lost night.
The "unknown git setting" report. Editors and credential managers write their own settings, so the upload report can fill up with lines you can't act on.
Two helper sessions in one folder. This is documented, but anyone running parallel helpers will hit it.
Since review 6, the timer false alarm (your own save being put back while a background job ran) is gone. A formatter's change of spaces only now stays.
3. Plain words
Setup's last line is misleading because of section 1. It says "changes to the guards need the owner's OK". You'd naturally read "guards" as including your tests, and by default they aren't guarded. The README's "a change to the kit, its settings or a check waits for your yes" has the same problem.
"Don't try another way round" ends every put-back message. It's fine for a cheating helper. An honest helper takes it as "give up" and stops for the night. Something like this would work better: "Leave a note for the owner in HANDOFF.md and carry on with other work."
The neutral box, the one with no weakening found, says "only you can OK a change to it". That's good. But an owner who sees it often learns to click Yes. Add one line saying what the change is, for example "a test's check changed from == 5 to >= 0".
"Taken as the owner's own change" appears in the catch log. To someone who doesn't code, that reads as "you did this". A clearer version: "changed while no helper step was running; the kit assumed it was you".
The guide's limits section is long, honest and mostly accurate. But "a change between steps is yours" (about git remote set-url) is now only partly true, because some git settings changed between steps are put back.
The README is good on "safety net, not a lock" and the beta label. Keep both on the first screen.
4. Release: what must change first
Setup has to guard the tests it finds, plus the test runner's settings, and show you the list. This matters more than anything else here. Every promise about weakened tests depends on it.
Make --solo honest about main, one way or the other.
A check-up command, something like fg/doctor.py. In plain words, it would say what's guarded, what isn't, whether GitHub branch protection is on, and whether the hooks are live. An owner who can't read foundationguard.json needs this.
A plain way for you to accept your own changes to a switch, behind the kit's box.
Put-back messages that point a stuck helper at other work instead of ending it.
A real Windows run of the check after every step (Git Bash and PowerShell), since that's where your games live. No review has run it there yet.
A human programmer's review before anyone else relies on it. The "AI-made, not reviewed" label is honest, but the bug in section 1 got past seven AI rounds because the setup step everyone tested wasn't the setup step a real user runs.
I couldn't check: anything on Windows, a real GitHub remote with branch protection, or a real AI session.
